Gemessen 06.10.2026, Runde 1 zu `claude/488-warm-page` (Playwright 1.55.1).

**Fixture-Reihenfolge (fixtureRunner.js `resolveParametersForFunction`):** erst alle Auto-Fixtures (worker-scoped vor test-scoped), dann die vom Test genannten. `_setupContextOptions` (auto, test-scoped) setzt `playwright._defaultContextOptions` und `_defaultContextTimeout = actionTimeout || 0`, BEVOR eine vom Test angeforderte Worker-Fixture `browser.newContext()` ruft. Folge: ein Context aus einer Worker-Fixture bekommt die gemergten `use`-Optionen und Timeout 0 auch ohne eigenes Options-Merging; die Liste in warm-page.js ist redundant, nicht falsch. `workerInfo.project.use` ist die gemergte Sicht (config.js: `mergeObjects(config.use, projectConfig.use, cli.use)`), Keys gemessen: baseURL, trace, screenshot, userAgent, viewport, screen, deviceScaleFactor, isMobile, hasTouch, defaultBrowserType, launchOptions.

**Probe-Rezept ohne Server (ca. 40 s, ohne Port 8080):** Scratchpad `probe.config.mjs` importiert die echte Config per `file:///…/testing/playwright.config.js`, spreadet sie, löscht `webServer`, setzt testDir/outputDir/retries 0/reporter list; Specs als `*.spec.mjs` importieren `test` per `file:///…/testing/warm-page.js` bzw. `file:///…/node_modules/@playwright/test/index.mjs` (gleiche Modulinstanz, kein Doppelladefehler). Aufruf `MHDBDB_TEST_PORT=8086 npx.cmd playwright test -c <abs. Pfad>`. Default-Action-Timeout messen: `Promise.race` aus `waitForSelector` ohne timeout und 36-s-Sleep; `page.context()._timeoutSettings._defaultTimeout` liest den Wert direkt (beide 0, warm wie eingebaut).

**Was am alten „jeder Test ein eigener Context" hing:** DEVELOPMENT.md:188 („since #318 there is exactly one [Node import]") zählt nach dem Opt-in zwei Importziele (`scripts/python-bin.js` aus zwei Specs, `../warm-page.js` aus reading-view); `tei-caching.spec.js:48` („isolierte Contexts") bleibt für diese Spec wahr. Retry läuft nach Fehlschlag in neuem Worker (dispatcher.js: `worker.stop(true)` bei `didFail`), also kalt. Storage im Hauptsite-JS: nur `mhdbdb-results-view` (app.js) und `localStorage.clear()` in site-chrome.js; kein Service Worker.

**Laufzeitangaben (Runde 2, 06.10.2026):** die Sekundenzahl in der `stats:`-Zeile von `scripts/run-tests.js` ist `report.json` → `stats.duration`; Playwrights Uhr dafür startet in `InternalReporter.onConfigure` (tasks.js:78, vor `taskRunner.run`), also **vor** dem `webServer`-Plugin-Setup (tasks.js:104/138). Sie enthält den Serverstart. Gegen die Wanduhr um `npm test` gemessen 1,8 s und 1,7 s Abstand (424,8/423, 451,7/450). Die 487/519 s vom 24.09. sind laut #488-Kommentar Wanduhr um den ganzen Aufruf; beide Skalen sind damit bis auf ~2 s vergleichbar. Zwei Volläufe auf gleicher Testzahl streuen um 32 s (24.09.), ein Einzellauf-Paar belegt deshalb keinen Gewinn unter 32 s.

**Runde 3 (06.10.2026, fünf weitere Specs, Teardown `localStorage.clear()`):** Playwright 1.55.1 gemessen: nach `didFail` stoppt der Dispatcher den Worker (`dispatcher.js:110-113`, `worker.stop(true)`), der Retry läuft kalt; nach Test-Timeout bekommt der Fixture-Teardown einen eigenen Slot (`workerMain.js:355-357`); Dialoge ohne Listener werden auto-dismissed (`browserContext.js:122`). App-Storage: `localStorage.(get|set|remove)Item` in 3 Dateien (app.js `mhdbdb-results-view`, playground-main.js:621/641 `mhdbdb-playground-section-<panel>`, lemma/index.html:98 nur `getItem` matomo-optout); `deleteDatabase('MHDBDB_Playground')` in playground-main.js:221 ist Altlast-Löschung (#314); Playground nutzt denselben `assets/js/lib/corpus-loader.js` (`MHDBDBMainSite`, Versionscheck). Die 450-s-Zahl stammt aus dem Agenten-Worktree `771d91de3` (error-handling schon ohne feste Waits, 435 Tests, 0 flaky).
