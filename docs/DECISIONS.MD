# Architecture Decision Records

This document records major architectural decisions for the MHDBDB TEI Repository, following the ADR template: Context → Problem → Alternatives → Decision → Consequences.

## ADR-001: Migration from Runtime XML Parsing to Pre-Built Indexes

**Status:** Implemented (September 2025)
**Context:** Browser-based corpus search with large XML authority files

### Problem

The project initially loaded 7 XML authority files (47.3 MB total) directly in the browser and parsed them at runtime. This caused several issues:
- 30-second initial load time
- High memory usage (DOM trees for 7 large XML files)
- Complex XPath queries for cross-reference resolution
- Browser crashes on slower devices

### Alternatives Evaluated

**Option A: Keep runtime XML parsing**
- Pro: Direct access to source data, no build step
- Pro: Easy to update (just replace XML files)
- Con: Slow initial load (30 seconds)
- Con: High memory usage
- Rejected: User experience unacceptable

**Option B: Backend API with XML parsing**
- Pro: Server handles heavy processing
- Pro: Instant client load
- Con: Requires server hosting and maintenance
- Con: Monthly hosting costs
- Con: Backend logic in separate language
- Rejected: Project requirement for free hosting

**Option C: Pre-built JSON indexes**
- Pro: 19× smaller download (47MB → 2.9MB compressed)
- Pro: Instant parsing (no XML DOM creation)
- Pro: Direct object access (no XPath queries)
- Con: Requires Python build step
- Con: Two-stage workflow (source XML → index → browser)
- **Accepted:** Best balance of performance and cost

### Decision

Implement pre-built JSON indexes generated by Python scripts at build time:
- `build-authority-index.py` extracts data from 7 XML files
- Output: `authority-index.json.gz` (2.90 MB compressed)
- Browser fetches compressed JSON, decompresses, parses
- IndexedDB caches with 30-day expiration

### Consequences

**Positive:**
- 19× smaller download (47.3 MB → 2.9 MB)
- Instant parsing (JSON.parse vs XML DOM creation)
- Lower memory usage (JavaScript objects vs DOM trees)
- Simpler client code (direct access vs XPath queries)
- Faster subsequent loads (IndexedDB caching)

**Negative:**
- Requires Python 3.13+ for building indexes
- Two-stage workflow (modify XML → rebuild index → deploy)
- Cache invalidation requires version increment
- Build time ~30 seconds per index

**Mitigations:**
- Pre-built indexes committed to repository (Python optional for most developers)
- Clear build documentation in DEVELOPMENT.MD
- Automated validation to catch build errors

## ADR-002: Phase 7 Modular UI Refactoring

**Status:** Implemented (October 2, 2025)
**Context:** Playground UI with monolithic JavaScript files

### Problem

Playground UI code concentrated in large files:
- `playground-ui.js` (2,800 lines) - All UI logic
- `authority-explorers.js` (1,500 lines) - Six explorers in one file
- Hard to maintain and extend
- Difficult to test individual components
- High cognitive load for new developers

### Alternatives Evaluated

**Option A: Keep monolithic structure**
- Pro: Simple file structure
- Con: Hard to maintain
- Con: Difficult to test
- Rejected: Not scalable

**Option B: Component framework (React, Vue, Svelte)**
- Pro: Modern patterns, reusable components
- Con: Adds build step and dependencies
- Con: Steeper learning curve
- Con: Breaks "no framework" principle
- Rejected: Project prefers vanilla JS

**Option C: Modular vanilla JS (ES6 modules)**
- Pro: Native browser support
- Pro: Clear separation of concerns
- Pro: Easy to test
- Con: More files to navigate
- **Accepted:** Best for maintainability

### Decision

Decompose monolithic files into 18 specialized modules organized by feature:
```
ui/
├── core/              # Core utilities (3 modules)
├── authority/         # Authority explorers (6 modules)
├── tei/               # TEI analysis (2 modules)
└── search/            # Search utilities (1 module)
```

Each explorer gets dedicated file (person-explorer.js, work-explorer.js, etc.)

### Consequences

**Positive:**
- 5,536 lines removed from codebase
- Clear separation of concerns
- Each module focused on single responsibility
- Easier to test (unit test individual modules)
- Improved maintainability
- Reusable patterns across explorers

**Negative:**
- More files to navigate (18 modules vs 3 large files)
- Slightly more imports/exports
- Requires module-aware development

**Mitigations:**
- Clear directory structure (core/, authority/, tei/, search/)
- Consistent naming conventions
- Module index files for easy imports

## ADR-003: Corpus Index v4.0.0 - Document-Level Word Indexing

**Status:** Implemented (October 5, 2025)
**Context:** Multi-lemma proximity search accuracy

### Problem

Corpus index v3.x used paragraph-based word indexing:
- Words indexed with paragraph-level positions (paragraph 5, word 3)
- Python extraction and JavaScript parsing counted words differently
- Position misalignment caused proximity search to miss results
- Complex coordinate system (paragraph + word position)

### Alternatives Evaluated

**Option A: Fix paragraph position alignment**
- Pro: Keeps paragraph structure
- Con: Requires synchronizing Python and JavaScript word counting
- Con: Edge cases (paragraphs with mixed annotated/unannotated words)
- Rejected: Too complex

**Option B: Sentence-level indexing**
- Pro: Finer granularity than paragraphs
- Con: Same alignment issues as paragraphs
- Con: TEI files don't always have sentence markup
- Rejected: Doesn't solve core problem

**Option C: Document-level indexing**
- Pro: Simple sequential positions (0, 1, 2, ...)
- Pro: Python and JavaScript can use identical extraction logic
- Pro: No coordinate system complexity
- Con: Loses paragraph structure information
- **Accepted:** Simplicity and accuracy more important

### Decision

Implement document-level word indexing in corpus index v4.0.0:
- Words indexed with simple sequential positions (0, 1, 2, ...)
- Extract via `//tei:body//tei:w[@lemmaRef]` in both Python and JavaScript
- Remove paragraph metadata entirely
- Proximity search uses document-level positions

### Consequences

**Positive:**
- 100% word coverage (all words in `<body>` indexed)
- Accurate proximity search (no position misalignment)
- Simpler architecture (no paragraph coordinates)
- ~30% smaller index size (removed paragraph metadata)
- Identical extraction logic in Python and JavaScript

**Negative:**
- Lost paragraph-level search mode
- Cannot filter by paragraph boundaries
- Context extraction spans paragraph breaks

**Mitigations:**
- Document and proximity modes cover most use cases
- Full-text reading view shows paragraph structure
- Paragraph mode was rarely used (based on usage analytics)

## ADR-004: IndexedDB Dual Expiration Policy

**Status:** Implemented (September 2025)
**Context:** Browser caching for performance

### Problem

Need to cache large data for performance, but balance freshness with storage:
- Authority indexes (3 MB) change infrequently
- User-uploaded TEI files should persist indefinitely
- IndexedDB has storage limits (~1 GB typical)
- Stale cache causes outdated search results

### Alternatives Evaluated

**Option A: No caching**
- Pro: Always fresh data
- Con: Slow performance (download every time)
- Rejected: Poor user experience

**Option B: Single expiration policy (7 days)**
- Pro: Simple to implement
- Con: User TEI files disappear after 7 days
- Rejected: Users expect persistent uploads

**Option C: Dual expiration policy**
- Pro: Fresh reference data, persistent user data
- Pro: Balances freshness and convenience
- Con: Slightly more complex
- **Accepted:** Best user experience

### Decision

Implement dual expiration policy in IndexedDB:
- **Authority/corpus indexes:** 30-day expiration (reference data)
- **User TEI files:** No expiration (user content)
- Version-based invalidation for indexes (increment version → refetch)

### Consequences

**Positive:**
- Fast subsequent loads (~100-200ms from cache)
- Fresh reference data (refetch after 30 days)
- User TEI files persist across sessions
- Manual version bump forces refetch when needed

**Negative:**
- More complex cache management code
- Users must manually clear cache if corrupted
- 30-day window may have stale data

**Mitigations:**
- Version increment in build scripts forces refetch
- Clear documentation for cache invalidation
- Future: Add "Clear cache" button in UI

## ADR-005: Three-Stage Lemma Resolution

**Status:** Implemented (September 2025)
**Context:** Orthographic variant handling in Middle High German

### Problem

Middle High German has extensive orthographic variation:
- Same word spelled dozens of ways ("brot", "brott", "broit", "brôt")
- No standardized spelling in medieval period
- Users expect to find all variants with single search
- Exact match insufficient for historical texts

### Alternatives Evaluated

**Option A: Fuzzy matching only**
- Pro: Catches all variations
- Con: Too many false positives
- Con: Performance issues (must compare to all lemmata)
- Rejected: Poor precision

**Option B: Variants dictionary only**
- Pro: Corpus-driven (uses attested forms)
- Pro: Fast O(1) lookup
- Con: Misses variants not in corpus
- Rejected: Incomplete coverage

**Option C: Three-stage resolution**
- Pro: Combines precision and recall
- Pro: Fast for common cases (exact match first)
- Con: More complex implementation
- **Accepted:** Best balance

### Decision

Implement 3-stage lemma resolution:
1. **Exact match in lexicon:** Check canonical forms first (fastest)
2. **Variants dictionary lookup:** Check 176k attested variants (O(1))
3. **Partial match fallback:** Fuzzy search if no exact match (catches edge cases)

### Consequences

**Positive:**
- 100% recall for orthographic variants
- Fast for common searches (exact match shortcircuits)
- Corpus-driven variants (uses real attestations)
- Fallback handles rare cases

**Negative:**
- More complex code (three lookup paths)
- Partial match can have false positives
- Variants dictionary requires periodic regeneration

**Mitigations:**
- Clear comments explaining each stage
- Variants regenerated automatically from corpus
- Partial match used only as fallback (rare)

## ADR-006: Client-Only Architecture (No Backend)

**Status:** Implemented (Initial release)
**Context:** Hosting and deployment strategy

### Problem

Need to host corpus search application with limited budget:
- Academic project with no hosting budget
- Requires global availability (researchers worldwide)
- Must be maintainable by small team
- Should be simple to deploy and update

### Alternatives Evaluated

**Option A: Traditional backend (Node.js + database)**
- Pro: Fast server-side processing
- Pro: Real-time updates
- Con: Monthly hosting costs (~$20-100)
- Con: Server maintenance burden
- Con: Requires backend expertise
- Rejected: No budget for hosting

**Option B: Serverless (AWS Lambda, Cloud Functions)**
- Pro: Pay-per-use pricing
- Pro: Scales automatically
- Con: Still costs money
- Con: Vendor lock-in
- Con: Complex deployment
- Rejected: Still has costs

**Option C: Client-only (GitHub Pages)**
- Pro: Free hosting
- Pro: No server maintenance
- Pro: Fast CDN distribution
- Con: All processing in browser
- Con: Large initial download
- **Accepted:** Only option with zero cost

### Decision

Implement client-only architecture with GitHub Pages hosting:
- All processing happens in browser
- Pre-built indexes loaded and cached
- No backend server required
- Automated deployment via GitHub Actions

### Consequences

**Positive:**
- Zero hosting cost (GitHub Pages free)
- No server maintenance
- Fast global CDN distribution
- Simple deployment (git push)
- No backend security concerns

**Negative:**
- Limited to browser memory (~2GB typical)
- Large initial download (~24 MB)
- No real-time updates (requires rebuild)
- Cannot perform server-side joins
- Search performance depends on client device

**Mitigations:**
- Pre-built indexes minimize download size
- IndexedDB caching for subsequent visits
- Clear browser requirements documented
- Future: Progressive loading for large corpus

## ADR-007: Multi-Lemma Reader Integration

**Status:** Implemented (October 6, 2025)
**Context:** Playground to main site navigation

### Problem

Researchers use playground for advanced proximity search but need immersive reading experience:
- Playground shows context snippets (±10 words)
- Researchers want full text with highlighting
- Context snippets lack surrounding narrative
- Manual navigation between playground and main site tedious

### Alternatives Evaluated

**Option A: Embed reader in playground**
- Pro: No navigation required
- Con: Duplicates reader code
- Con: Playground already complex
- Rejected: Violates DRY principle

**Option B: Open text in new tab (no parameters)**
- Pro: Simple implementation
- Con: Loses context (which lemmas, which position)
- Con: User must search again
- Rejected: Poor user experience

**Option C: URL parameters for cross-platform navigation**
- Pro: Preserves context (lemmas + position)
- Pro: Reuses existing reader code
- Pro: Seamless workflow
- Con: Requires URL parameter handling
- **Accepted:** Best user experience

### Decision

Implement URL parameter passing for cross-platform navigation:
- Playground generates URL: `korpus.html?textId=ABG&lemmaIds=879,7532&position=310`
- Main site reads parameters and opens text with:
  - Multi-lemma highlighting (5 colors)
  - Auto-scroll to exact position
  - Context navigation enabled

### Consequences

**Positive:**
- Seamless workflow (playground → main site)
- Preserves research context (lemmas + position)
- Immersive reading experience
- Reuses existing reader code
- Shareable URLs (researchers can share specific findings)

**Negative:**
- URL parameter parsing required
- Position tracking must be accurate
- Requires coordination between two codebases

**Mitigations:**
- Shared TextNormalizer and position tracking logic
- Clear documentation of URL parameter format
- Automated tests for parameter passing

## ADR-008: Desktop-Only Interface (No Mobile Optimization)

**Status:** Active decision
**Context:** Resource allocation and target audience

### Problem

Need to prioritize development resources:
- Limited development capacity (small team)
- Mobile responsive design requires significant effort
- Unclear if mobile use case is important for researchers

### Alternatives Evaluated

**Option A: Mobile-first design**
- Pro: Accessible on all devices
- Con: Significant redesign effort
- Con: Complex interactions hard on mobile
- Rejected: Not primary use case

**Option B: Responsive design (adapt to all screens)**
- Pro: Works on tablets and phones
- Con: Requires extensive CSS and testing
- Con: Some features hard to adapt (multi-column layout)
- Rejected: Resource intensive

**Option C: Desktop-only (minimum 1200px width)**
- Pro: Focus development on core features
- Pro: Optimize for primary use case (researchers at desks)
- Con: Not accessible on mobile
- **Accepted:** Prioritize quality over breadth

### Decision

Build desktop-only interface with minimum 1200px screen width:
- No mobile responsiveness
- Optimized for desktop research workflows
- Future mobile optimization when resources allow

### Consequences

**Positive:**
- Faster feature development
- Better desktop experience
- Simpler CSS (no media queries)
- Can use complex multi-column layouts

**Negative:**
- Not accessible on phones/tablets
- Limits potential audience
- May need redesign later for mobile

**Mitigations:**
- Document desktop requirement clearly
- Plan future mobile optimization
- Consider progressive web app (PWA) approach

## ADR-009: MHG Text Normalization Strategy

**Status:** Implemented (Initial release)
**Context:** Search consistency across historical texts

### Problem

Middle High German texts use diacritics and special characters:
- Long vowels: â, ê, î, ô, û
- Umlauts: ä, ö, ü
- Modern keyboards lack these characters
- Users type "a" but text has "â"
- Need consistent search behavior

### Alternatives Evaluated

**Option A: Require exact diacritics**
- Pro: Linguistically precise
- Con: Users can't type MHG characters easily
- Con: Poor search experience
- Rejected: Too restrictive

**Option B: Unicode normalization only**
- Pro: Simple implementation
- Con: Doesn't handle MHG-specific conversions
- Rejected: Incomplete solution

**Option C: Custom MHG normalization**
- Pro: Handles all MHG character variations
- Pro: User-friendly search
- Con: Custom implementation required
- **Accepted:** Best user experience

### Decision

Implement custom MHG text normalization:
- â→a, ê→e, î→i, ô→o, û→u (long vowels)
- ä→ae, ö→oe, ü→ue (umlauts)
- æ→ae, œ→oe (ligatures)
- Apply to all search inputs and indexed data
- Shared utility: `lib/text-normalizer.js`

### Consequences

**Positive:**
- User-friendly search (type "brot", find "brôt")
- Consistent behavior across 10 search entry points
- Simple keyboard input
- Works with English keyboards

**Negative:**
- Loses diacritic distinction (â and a treated same)
- Linguistically imprecise
- Some ambiguity (ü→ue might match different etymologies)

**Mitigations:**
- Normalization combined with variants dictionary (two-layer approach)
- Display shows original forms (â, ô, ü)
- Advanced users can still see distinctions in results

## ADR-006: Zotero API Integration for Bibliographic Metadata

**Status:** Implemented (October 2025)
**Context:** Bibliographic metadata management for 580+ works

### Problem

Works.xml contained incomplete bibliographic data with missing fields (edition, issue, seriesNumber) and inconsistent title casing. Manually maintaining biblStruct elements was error-prone and time-consuming.

### Alternatives Evaluated

**Option A: Manual XML editing**
- Pro: Direct control over data
- Con: Error-prone, time-consuming
- Con: No single source of truth
- Rejected: Not scalable

**Option B: Static Zotero XML export**
- Pro: Complete bibliographic data
- Con: Manual export process
- Con: No versioning/updates
- Rejected: Workflow too manual

**Option C: Zotero API with automated sync**
- Pro: Single source of truth (Zotero library)
- Pro: Complete field extraction (all metadata)
- Pro: Reproducible with caching
- Con: Requires API script
- **Accepted:** Best for data integrity

### Decision

Integrate Zotero API to fetch bibliographic metadata and update works.xml:
- Fetch from MHDBDB Zotero collection (group 5043625)
- Extract ALL fields: edition, volume, issue, series, seriesNumber, authors, editors
- Convert titles to German Title Case automatically
- Update ALL items (not just those with editors)
- Provide offline mode with caching for reproducibility

### Consequences

**Positive:**
- Complete metadata coverage: 680 biblStruct elements for 582 works
- Consistent German Title Case across all titles
- Single source of truth (Zotero library)
- Reproducible workflow with cache support
- All bibliographic fields now preserved (edition, seriesNumber, issue)

**Negative:**
- Requires Python script execution when Zotero data changes
- Two-step workflow: Zotero → works.xml → TEI headers
- API dependency (mitigated by cache)

**Implementation:** `scripts/data-wrangling/enhance_works_with_zotero.py`
