# Architecture Decision Records

This document records major architectural decisions for the MHDBDB TEI Repository, following the ADR template: Context → Problem → Alternatives → Decision → Consequences.

## ADR-001: Migration from Runtime XML Parsing to Pre-Built Indexes

**Status:** Implemented (September 2025)
**Context:** Browser-based corpus search with large XML authority files

### Problem

The project initially loaded the 7 content-bearing XML authority files (47.3 MB total; `contributors.xml` was only added later in 2026-04 and is not part of this story) directly in the browser and parsed them at runtime. This caused several issues:
- 30-second initial load time
- High memory usage (DOM trees for 7 large XML files)
- Complex XPath queries for cross-reference resolution
- Browser crashes on slower devices

### Alternatives Evaluated

**Option A: Keep runtime XML parsing**
- Pro: Direct access to source data, no build step
- Pro: Easy to update (just replace XML files)
- Con: Slow initial load (30 seconds)
- Con: High memory usage
- Rejected: User experience unacceptable

**Option B: Backend API with XML parsing**
- Pro: Server handles heavy processing
- Pro: Instant client load
- Con: Requires server hosting and maintenance
- Con: Monthly hosting costs
- Con: Backend logic in separate language
- Rejected: Project requirement for free hosting

**Option C: Pre-built JSON indexes**
- Pro: ~15× smaller download (47.3 MB → ~3.1 MB compressed)
- Pro: Instant parsing (no XML DOM creation)
- Pro: Direct object access (no XPath queries)
- Con: Requires Python build step
- Con: Two-stage workflow (source XML → index → browser)
- **Accepted:** Best balance of performance and cost

### Decision

Implement pre-built JSON indexes generated by Python scripts at build time:
- `build-authority-index.py` extracts data from the 7 content-bearing XML files (contributors.xml is not indexed: it is project-internal editor attribution, not search content)
- Output: `authority-index.json.gz` (~3.1 MB compressed; for the current version see TEI-MODEL.md §11)
- Browser fetches compressed JSON, decompresses, parses
- IndexedDB caches with 30-day expiration

### Consequences

**Positive:**
- ~15× smaller download (47.3 MB → ~3.1 MB)
- Instant parsing (JSON.parse vs XML DOM creation)
- Lower memory usage (JavaScript objects vs DOM trees)
- Simpler client code (direct access vs XPath queries)
- Faster subsequent loads (IndexedDB caching)

**Negative:**
- Requires Python 3.13+ for building indexes
- Two-stage workflow (modify XML → rebuild index → deploy)
- Cache invalidation requires version increment
- Build time: ~12 s for the authority index, ~46 s for the corpus index with 8 worker
  processes (~184 s sequential); the full chain including variants.xml and the JSON API
  takes ~85 s (measured 2026-07-31 on 667 files, see #284). Which of those steps a given
  change actually needs: DATA-MODEL.md, "Routing nach Änderungstyp" (routing by type of change)

**Mitigations:**
- Pre-built indexes committed to repository (Python optional for most developers)
- Clear build documentation in DEVELOPMENT.md
- Automated validation to catch build errors

## ADR-002: Phase 7 Modular UI Refactoring

**Status:** Implemented (October 2, 2025)
**Context:** Playground UI with monolithic JavaScript files

### Problem

Playground UI code concentrated in large files:
- `playground-ui.js` (2,800 lines) - All UI logic
- `authority-explorers.js` (1,500 lines) - Six explorers in one file
- Hard to maintain and extend
- Difficult to test individual components
- High cognitive load for new developers

### Alternatives Evaluated

**Option A: Keep monolithic structure**
- Pro: Simple file structure
- Con: Hard to maintain
- Con: Difficult to test
- Rejected: Not scalable

**Option B: Component framework (React, Vue, Svelte)**
- Pro: Modern patterns, reusable components
- Con: Adds build step and dependencies
- Con: Steeper learning curve
- Con: Breaks "no framework" principle
- Rejected: Project prefers vanilla JS

**Option C: Modular vanilla JS (ES6 modules)**
- Pro: Native browser support
- Pro: Clear separation of concerns
- Pro: Easy to test
- Con: More files to navigate
- **Accepted:** Best for maintainability

### Decision

Decompose monolithic files into specialized modules organized by feature. On the day of the decision (measured against the tree of `ae80175c4`) there were 13 modules in total:
```
ui/
├── core/              # Core utilities (3 modules)
├── authority/         # Authority explorers (7 modules)
├── tei/               # TEI analysis (2 modules: tei-ui.js, multi-lemma-search.js)
└── search/            # Search utilities (1 module)
```
`core/` later gained the hash router (#48), and from May 2026 `tei/` filled up with the analysis tools. The current state is held by the module tree in [ARCHITECTURE.md](ARCHITECTURE.md#ui-layer-phase-7-modular-architecture); this ADR describes the decision, not today's inventory.

Each explorer gets dedicated file (person-explorer.js, work-explorer.js, etc.)

### Consequences

**Positive:**
- 5,536 lines removed from codebase
- Clear separation of concerns
- Each module focused on single responsibility
- Easier to test (unit test individual modules)
- Improved maintainability
- Reusable patterns across explorers

**Negative:**
- More files to navigate (13 modules instead of the two monoliths above; the number has grown to a multiple of that since then, see ARCHITECTURE.md)
- Slightly more imports/exports
- Requires module-aware development

**Mitigations:**
- Clear directory structure (core/, authority/, tei/, search/)
- Consistent naming conventions
- Module index files for easy imports

## ADR-003: Corpus Index v4.0.0 - Document-Level Word Indexing

**Status:** Implemented (October 5, 2025)
**Context:** Multi-lemma proximity search accuracy

### Problem

Corpus index v3.x used paragraph-based word indexing:
- Words indexed with paragraph-level positions (paragraph 5, word 3)
- Python extraction and JavaScript parsing counted words differently
- Position misalignment caused proximity search to miss results
- Complex coordinate system (paragraph + word position)

### Alternatives Evaluated

**Option A: Fix paragraph position alignment**
- Pro: Keeps paragraph structure
- Con: Requires synchronizing Python and JavaScript word counting
- Con: Edge cases (paragraphs with mixed annotated/unannotated words)
- Rejected: Too complex

**Option B: Sentence-level indexing**
- Pro: Finer granularity than paragraphs
- Con: Same alignment issues as paragraphs
- Con: TEI files don't always have sentence markup
- Rejected: Doesn't solve core problem

**Option C: Document-level indexing**
- Pro: Simple sequential positions (0, 1, 2, ...)
- Pro: Python and JavaScript can use identical extraction logic
- Pro: No coordinate system complexity
- Con: Loses paragraph structure information
- **Accepted:** Simplicity and accuracy more important

### Decision

Implement document-level word indexing in corpus index v4.0.0:
- Words indexed with simple sequential positions (0, 1, 2, ...)
- Extract via `//tei:body//tei:w[@lemmaRef]` in both Python and JavaScript
- Remove paragraph metadata entirely
- Proximity search uses document-level positions

### Consequences

**Positive:**
- Complete coverage of the annotated words (every `<w>` with a non-empty `@lemmaRef` and text content is indexed; this matches the position-counting hard constraint, see CONTRACTS.md §B)
- Accurate proximity search (no position misalignment)
- Simpler architecture (no paragraph coordinates)
- ~30% smaller index size (removed paragraph metadata)
- Identical extraction logic in Python and JavaScript

**Negative:**
- Lost paragraph-level search mode
- Cannot filter by paragraph boundaries
- Context extraction spans paragraph breaks

**Mitigations:**
- Document and proximity modes cover most use cases
- Full-text reading view shows paragraph structure
- Paragraph mode was rarely used (based on usage analytics)

## ADR-004: IndexedDB Dual Expiration Policy

**Status:** Implemented (September 2025), half of it moot since #314 (2026-07-31): the branch "user TEI files persist indefinitely" was justified by the playground's file upload, which no longer exists. The 30-day expiration for the authority and corpus indexes applies unchanged
**Context:** Browser caching for performance

### Problem

Need to cache large data for performance, but balance freshness with storage:
- Authority indexes (3 MB) change infrequently
- User-uploaded TEI files should persist indefinitely
- IndexedDB has storage limits (~1 GB typical)
- Stale cache causes outdated search results

### Alternatives Evaluated

**Option A: No caching**
- Pro: Always fresh data
- Con: Slow performance (download every time)
- Rejected: Poor user experience

**Option B: Single expiration policy (7 days)**
- Pro: Simple to implement
- Con: User TEI files disappear after 7 days
- Rejected: Users expect persistent uploads

**Option C: Dual expiration policy**
- Pro: Fresh reference data, persistent user data
- Pro: Balances freshness and convenience
- Con: Slightly more complex
- **Accepted:** Best user experience

### Decision

Implement dual expiration policy in IndexedDB:
- **Authority/corpus indexes:** 30-day expiration (reference data)
- **User TEI files:** No expiration (user content)
- Version-based invalidation for indexes (increment version → refetch)

### Consequences

**Positive:**
- Fast subsequent loads (~100-200ms from cache)
- Fresh reference data (refetch after 30 days)
- User TEI files persist across sessions
- Manual version bump forces refetch when needed

**Negative:**
- More complex cache management code
- Users must manually clear cache if corrupted
- 30-day window may have stale data

**Mitigations:**
- Version increment in build scripts forces refetch
- Clear documentation for cache invalidation
- Future: Add "Clear cache" button in UI

## ADR-005: Three-Stage Lemma Resolution

**Status:** Implemented (September 2025)
**Context:** Orthographic variant handling in Middle High German

### Problem

Middle High German has extensive orthographic variation:
- Same word spelled dozens of ways ("brot", "brott", "broit", "brôt")
- No standardized spelling in medieval period
- Users expect to find all variants with single search
- Exact match insufficient for historical texts

### Alternatives Evaluated

**Option A: Fuzzy matching only**
- Pro: Catches all variations
- Con: Too many false positives
- Con: Performance issues (must compare to all lemmata)
- Rejected: Poor precision

**Option B: Variants dictionary only**
- Pro: Corpus-driven (uses attested forms)
- Pro: Fast O(1) lookup
- Con: Misses variants not in corpus
- Rejected: Incomplete coverage

**Option C: Three-stage resolution**
- Pro: Combines precision and recall
- Pro: Fast for common cases (exact match first)
- Con: More complex implementation
- **Accepted:** Best balance

### Decision

Implement 3-stage lemma resolution:
1. **Exact match in lexicon:** Check canonical forms first (fastest)
2. **Variants dictionary lookup:** normalized mappings, deduplicated from the raw forms in `variants.xml`, so noticeably fewer mappings than forms (O(1); current figures in [CONTRACTS §C](CONTRACTS.md#c-3-stage-lemma-resolution-algorithm))
3. **Partial match fallback:** Fuzzy search if no exact match (catches edge cases)

### Consequences

**Positive:**
- 100% recall for orthographic variants
- Fast for common searches (exact match shortcircuits)
- Corpus-driven variants (uses real attestations)
- Fallback handles rare cases

**Negative:**
- More complex code (three lookup paths)
- Partial match can have false positives
- Variants dictionary requires periodic regeneration

**Mitigations:**
- Clear comments explaining each stage
- Variants regenerated from the corpus via `scripts/sync/extract-variants.py --apply` (#44/#115), run after corpus changes, then authority-index rebuild + version bump
- Partial match used only as fallback (rare)

> **Correction 2026-05-29:** an earlier version claimed „Variants regenerated automatically from corpus". That was wrong: the original extractor only existed on the archived `initial-data-wrangling` branch and read the pre-#32 `@wordRef`, so it never ran against the migrated corpus. `variants.xml` drifted by 64,287 variant forms because of this, until on 2026-05-29 the maintained generator `scripts/sync/extract-variants.py` (`@corresp`-based) was added and the file regenerated (192,472 → 256,759 variant forms). There is **no** automatic trigger; regeneration is a manual lifecycle step (see [DATA-MODEL.md → Data-Change-Lifecycle](DATA-MODEL.md#data-change-lifecycle)). Unlike variants, the **lemma/sense backfill** (#115) cannot be fully automated: lemma stubs can be generated from the corpus, the sense-to-concept assignment stays curatorial (see [ADR-015](#adr-015-authority-source-model-the-corpus-leads-ingest-needs-a-backward-sync)).

## ADR-006: Client-Only Architecture (No Backend)

**Status:** Implemented (Initial release)
**Context:** Hosting and deployment strategy

### Problem

Need to host corpus search application with limited budget:
- Academic project with no hosting budget
- Requires global availability (researchers worldwide)
- Must be maintainable by small team
- Should be simple to deploy and update

### Alternatives Evaluated

**Option A: Traditional backend (Node.js + database)**
- Pro: Fast server-side processing
- Pro: Real-time updates
- Con: Monthly hosting costs (~$20-100)
- Con: Server maintenance burden
- Con: Requires backend expertise
- Rejected: No budget for hosting

**Option B: Serverless (AWS Lambda, Cloud Functions)**
- Pro: Pay-per-use pricing
- Pro: Scales automatically
- Con: Still costs money
- Con: Vendor lock-in
- Con: Complex deployment
- Rejected: Still has costs

**Option C: Client-only (GitHub Pages)**
- Pro: Free hosting
- Pro: No server maintenance
- Pro: Fast CDN distribution
- Con: All processing in browser
- Con: Large initial download
- **Accepted:** Only option with zero cost

### Decision

Implement client-only architecture with GitHub Pages hosting:
- All processing happens in browser
- Pre-built indexes loaded and cached
- No backend server required
- Automated deployment via GitHub Actions

### Consequences

**Positive:**
- Zero hosting cost (GitHub Pages free)
- No server maintenance
- Fast global CDN distribution
- Simple deployment (git push)
- No backend security concerns

**Negative:**
- Limited to browser memory (~2GB typical)
- Large initial download (~43 MB indexes: 3 MB authority + 40 MB corpus, gzipped)
- No real-time updates (requires rebuild)
- Cannot perform server-side joins
- Search performance depends on client device

**Mitigations:**
- Pre-built indexes minimize download size
- IndexedDB caching for subsequent visits
- Clear browser requirements documented
- Future: Progressive loading for large corpus

## ADR-007: Multi-Lemma Reader Integration

**Status:** Implemented (October 6, 2025)
**Context:** Playground to main site navigation

### Problem

Researchers use playground for advanced proximity search but need immersive reading experience:
- Playground shows context snippets (±10 words)
- Researchers want full text with highlighting
- Context snippets lack surrounding narrative
- Manual navigation between playground and main site tedious

### Alternatives Evaluated

**Option A: Embed reader in playground**
- Pro: No navigation required
- Con: Duplicates reader code
- Con: Playground already complex
- Rejected: Violates DRY principle

**Option B: Open text in new tab (no parameters)**
- Pro: Simple implementation
- Con: Loses context (which lemmas, which position)
- Con: User must search again
- Rejected: Poor user experience

**Option C: URL parameters for cross-platform navigation**
- Pro: Preserves context (lemmas + position)
- Pro: Reuses existing reader code
- Pro: Seamless workflow
- Con: Requires URL parameter handling
- **Accepted:** Best user experience

### Decision

Implement URL parameter passing for cross-platform navigation:
- Playground generates URL: `korpus.html?textId=ABG&lemmaIds=879,7532&position=310`
- Main site reads parameters and opens text with:
  - Multi-lemma highlighting (5 colors)
  - Auto-scroll to exact position
  - Context navigation enabled

### Consequences

**Positive:**
- Seamless workflow (playground → main site)
- Preserves research context (lemmas + position)
- Immersive reading experience
- Reuses existing reader code
- Shareable URLs (researchers can share specific findings)

**Negative:**
- URL parameter parsing required
- Position tracking must be accurate
- Requires coordination between two codebases

**Mitigations:**
- Shared TextNormalizer and position tracking logic
- Clear documentation of URL parameter format
- Automated tests for parameter passing

## ADR-009: MHG Text Normalization Strategy

**Status:** Implemented (Initial release)
**Context:** Search consistency across historical texts

### Problem

Middle High German texts use diacritics and special characters:
- Long vowels: â, ê, î, ô, û
- Umlauts: ä, ö, ü
- Modern keyboards lack these characters
- Users type "a" but text has "â"
- Need consistent search behavior

### Alternatives Evaluated

**Option A: Require exact diacritics**
- Pro: Linguistically precise
- Con: Users can't type MHG characters easily
- Con: Poor search experience
- Rejected: Too restrictive

**Option B: Unicode normalization only**
- Pro: Simple implementation
- Con: Doesn't handle MHG-specific conversions
- Rejected: Incomplete solution

**Option C: Custom MHG normalization**
- Pro: Handles all MHG character variations
- Pro: User-friendly search
- Con: Custom implementation required
- **Accepted:** Best user experience

### Decision

Implement custom MHG text normalization:
- â→a, ê→e, î→i, ô→o, û→u (long vowels)
- ä→ae, ö→oe, ü→ue (umlauts)
- æ→ae, œ→oe (ligatures)
- Apply to all search inputs and indexed data
- Shared utility: `assets/js/lib/text-normalizer.js`

### Consequences

**Positive:**
- User-friendly search (type "brot", find "brôt")
- Consistent behavior across 10 search entry points
- Simple keyboard input
- Works with English keyboards

**Negative:**
- Loses diacritic distinction (â and a treated same)
- Linguistically imprecise
- Some ambiguity (ü→ue might match different etymologies)

**Mitigations:**
- Normalization combined with variants dictionary (two-layer approach)
- Display shows original forms (â, ô, ü)
- Advanced users can still see distinctions in results

## ADR-010: Zotero API Integration for Bibliographic Metadata

**Status:** Implemented (October 2025)
**Context:** Bibliographic metadata management for 580+ works

### Problem

Works.xml contained incomplete bibliographic data with missing fields (edition, issue, seriesNumber) and inconsistent title casing. Manually maintaining biblStruct elements was error-prone and time-consuming.

### Alternatives Evaluated

**Option A: Manual XML editing**
- Pro: Direct control over data
- Con: Error-prone, time-consuming
- Con: No single source of truth
- Rejected: Not scalable

**Option B: Static Zotero XML export**
- Pro: Complete bibliographic data
- Con: Manual export process
- Con: No versioning/updates
- Rejected: Workflow too manual

**Option C: Zotero API with automated sync**
- Pro: Single source of truth (Zotero library)
- Pro: Complete field extraction (all metadata)
- Pro: Reproducible with caching
- Con: Requires API script
- **Accepted:** Best for data integrity

### Decision

Integrate Zotero API to fetch bibliographic metadata and update works.xml:
- Fetch from MHDBDB Zotero collection (group 5043625)
- Extract ALL fields: edition, volume, issue, series, seriesNumber, authors, editors
- Convert titles to German Title Case automatically
- Update ALL items (not just those with editors)
- Provide offline mode with caching for reproducibility

### Consequences

**Positive:**
- Complete metadata coverage: 680 biblStruct elements for 582 works
- Consistent German Title Case across all titles
- Single source of truth (Zotero library)
- Reproducible workflow with cache support
- All bibliographic fields now preserved (edition, seriesNumber, issue)

**Negative:**
- Requires Python script execution when Zotero data changes
- Two-step workflow: Zotero → works.xml → TEI headers
- API dependency (mitigated by cache)

**Implementation:** `scripts/sync/enhance_works_with_zotero.py`

## ADR-011: Browser-Level Scrolling for Korpus Reading View

**Status:** Implemented (October 2025)
**Context:** Main site korpus.html 3-column grid layout with reading panel

### Problem

The korpus.html reading view initially used container-level scrolling with `overflow-y: auto` and `max-height` constraints on individual sections (results list, reading body, metadata accordion). This caused UX issues:
- Multiple scrollbars (confusing for users)
- Metadata accordion content trapped in fixed-height container (not fully readable)
- Unequal column heights (unprofessional appearance)
- Scroll-to-highlight broke when highlighting search results (scrolled container instead of browser)

### Alternatives Evaluated

**Option A: Keep container scrolling**
- Pro: Each section independently scrollable
- Pro: Header remains visible while scrolling
- Con: Multiple scrollbars (poor UX)
- Con: Metadata accordion constrained
- Con: Unequal column heights
- Rejected: Users prefer single browser scrollbar

**Option B: Browser-level scrolling**
- Pro: Single scrollbar (better UX)
- Pro: Natural content flow
- Pro: Metadata accordion fully readable
- Pro: Equal-height columns via CSS Grid
- Con: Sticky header needed to keep navigation visible
- **Accepted:** Standard web UX pattern, preferred by users

### Decision

Remove all container-level scrolling constraints and use browser-level scrolling:
- Remove `max-height` and `overflow-y: auto` from all containers
- Remove `flex-shrink-0` constraints that limited layout
- Use CSS Grid with `align-items: start` for equal-height columns
- Update `scrollToHighlight()` to use `window.scrollTo()` with 120px header offset
- Keep sticky header for navigation

### Consequences

**Positive:**
- Single browser scrollbar (standard UX)
- Metadata accordion fully readable when expanded
- Equal-height columns (professional appearance)
- Scroll-to-highlight works correctly
- Natural content flow

**Negative:**
- Header scrolls out of view (mitigated by sticky positioning)
- Longer pages require more scrolling (acceptable trade-off)

**Files Modified:**
- `korpus.html` - Removed max-height inline styles
- `assets/css/korpus.css` - Removed overflow-y and max-height from `.reading-body` and `.metadata-sections`
- `assets/js/rendering/tei-text-reader.js` - Changed scrollToHighlight() from container to window scrolling

For data structures, see [DATA-MODEL.md](DATA-MODEL.md).

## ADR-012: Provenance Model for Digital Intermediaries

**Date:** 2026-02-24
**Status:** Accepted (implemented in #35, #37, #38, #39, #40)

### Problem

~55 TEI files derive from third-party digital intermediaries (e-texts), not directly from print editions. The actual chain is: Print Edition → Digital Intermediate → MHDBDB TEI. Previously documented only as unstructured prose in `<note>` elements – not machine-readable, not consistent.

### Alternatives Considered

| Approach | Mechanism | Rejected because |
|----------|-----------|-----------------|
| A. Flat `<listBibl>` | Multiple `<bibl>` siblings | No explicit derivation direction |
| B. Nested `<relatedItem>` | `<bibl>` inside `<biblStruct>` | Inverts derivation direction; harder to query |
| C. `<biblFull>` | Full file description | Overkill for HTML/OCR sources (TEI P5 2.2.8 recommends only for TEI→TEI) |
| **D. Flat + `@corresp`** | **Siblings with cross-reference** | **Chosen** |

### Decision

**Approach D**: Add `<bibl type="digitalIntermediary">` as sibling to existing `<biblStruct>` inside `<listBibl>`, with `@corresp` linking to the print edition it derives from.

```xml
<bibl type="digitalIntermediary" xml:id="{SIGLE}_etext"
      corresp="#{SIGLE}_{SIGLE}">
  <title>Elektronische Zwischenstufe</title>
  <respStmt>
    <resp>{responsibility}</resp>
    <name>{person or orgName}</name>
  </respStmt>
  <date when="{date}">{display date}</date>
  <ref target="{URL}"/>
  <note type="provenance">{relationship description}</note>
  <note type="fidelity">{transcription accuracy note}</note>
</bibl>
```

**Dual provenance** (e.g., FWWB, GSP, KDO, KME – Gloning → Klug chain): Two `<bibl>` elements where the second `@corresp` points to the first intermediary, not the print edition.

### Consequences

**Positive:** Existing `<biblStruct>` untouched – zero impact on build scripts, JS rendering, or index generation. `@type="digitalIntermediary"` enables programmatic filtering. 5 provider groups documented (Klug, Harsch, TITUS, Gloning, Virginia/Trier).

**Negative:** `@corresp` implies bidirectional relationship – derivation direction inferred from context, not from TEI semantics.

## ADR-013: Data Consolidation Before Schema Relaxation

**Date:** 2026-04-15
**Status:** Accepted (codified as Hard Constraint in `CLAUDE.md`, commit `9ab92cdb2`)
**Context:** Schema/data conflicts discovered during #32-followup cleanup

### Problem

When the schema (`schema/mhdbdb.rnc` or `schema/mhdbdb-authority.rnc`) is stricter than the data on disk – or the data contains structures that make validation pathologically slow – there are two ways to resolve the conflict:

- **A.** Make the schema more permissive to accommodate the data as-is.
- **B.** Migrate the data to match the stricter, cleaner schema.

Two concrete cases forced the decision on 2026-04-15:

1. **PL1/PL2/PL3 (Prosa-Lancelot)**: each file carried its entire body text in a single `<p>` with 240k–404k direct children. The recursive `<hi>/<inline.model>` content model caused `lxml.etree.RelaxNG` validation of PL1 alone to take 339 seconds (OVG, 62.9 MB vs. PL1 45 MB, validated in 7.5 s – so not a size issue but a structural backtracking issue). Option A would have been to refactor the schema. Option B was to split the mega-`<p>` at `<pb/>` milestones.

2. **143 files with nested `<hi>/<hi>`**: the recursive content model (`hi = element hi { ..., mixed { inline.model* } }` where `inline.model` contains `hi`) existed because some legacy data had nested highlights. Option A would have been to keep the recursion. Option B was to flatten all 36,924 nested instances and then tighten the schema to a non-recursive `hi.content.model`.

### Alternatives Considered

| Approach | Mechanism | Pros | Cons |
|----------|-----------|------|------|
| **A. Schema-First** (schema adapts to data) | Add GAP patterns, permissive content models, `*`-cardinalities | Zero data churn, no migration scripts | Schema drifts away from TEI idioms; future data can follow the same anti-patterns; validators stay slow on pathological data |
| **B. Data-First** (data migrates to schema) | One-shot migration scripts in `scripts/`, moved to `scripts/_archived/` after run | Schema stays tight and idiomatic; data becomes consistently structured; future ingests inherit the cleaner patterns; validation performance improves | Migration risk (must be idempotent + reversible via git); requires owner consent to touch corpus files |
| C. Permanent parallel schemas | Two schemas: a tight "canonical" and a loose "legacy-compatible" | – | Doubles validation effort; drift between the two over time |

### Decision

**Approach B** is the project default for all future schema/data conflicts. Schema relaxation is only acceptable as a documented `GAP` comment in the RNC source when a data migration would be disproportionately expensive or semantically dangerous (e.g., the 30 corpus files currently covered by GAPs 1–11, which represent intentional encoding choices for specific text genres).

The policy is codified in `CLAUDE.md` under "Hard Constraints":

> **Daten vor Schema**: Bei Konflikten zwischen Bestandsdaten (Korpus, Authority-Files) und dem Schema immer zuerst die Daten migrieren, nicht das Schema aufweichen. Eine Schema-Lockerung ist nur zulässig, wenn die Daten-Migration unverhältnismäßig teuer oder semantisch gefährlich wäre – und dann explizit als `GAP`-Kommentar im Schema dokumentiert (siehe `schema/mhdbdb.rnc` GAPs 1–11).

### Implementation (2026-04-15)

Both motivating cases were resolved in single day:

| Case | Data migration commit | Schema consequence |
|------|----------------------|--------------------|
| PL1/PL2/PL3 mega-`<p>` split | `49d7b58aa` (script `scripts/_archived/split-prose-mega-p.py`) | None – content model was already permissive. Validation of PL1 went from 339 s → 1.38 s (245× faster). |
| Nested `<hi>` flatten across 143 files | `b3e76ce7b` (script `scripts/_archived/flatten-nested-hi.py`) | `38b0bdd10`: new `hi.content.model` pattern in `mhdbdb.rnc` that is `inline.model` minus `hi` – removes the recursion entirely. |

36,924 nested-`<hi>` instances were migrated, net `<hi>` element-count reduction ~36,500. All element counts for `<w>`, `<pc>`, `<lb>`, `<pb>`, `<supplied>` unchanged (no data loss). Full corpus validation after both migrations: 30/666 stage-1 fails (unchanged #30 baseline), 0/666 stage-2 fails. Total corpus validation time: 830 s (at start of day) → 493 s (end of day), ~40 % faster.

### Consequences

**Positive:**
- Schema stays readable and idiomatic-TEI. No accidental permissiveness.
- One-shot migration scripts are archived under `scripts/_archived/` with full commit context, so future contributors can see exactly what transformation happened.
- Validation speed improvements are structural – every future schema change now runs against cleaner data.
- New ingests inherit the tighter structure (one `<p>` per page for prose, flat `<hi>` throughout) – the "example file" pattern in `schema/examples/` carries the cleaner shape.

**Negative:**
- Data migrations must be done **very** carefully: byte-level sanity checks (element counts before/after), sample-first + full run, targeted validation after. That day's split-prose-mega-p.py run hit a subtle CRLF-on-Windows bug in `Path.write_text()` that produced a 14.6-million-line spurious diff before being rewritten to use `Path.write_bytes()` with dynamic newline detection.
- Archives accumulate: after each migration, the one-shot script lives forever in `scripts/_archived/` as documentation. Tolerable so far (~4 scripts), could become noise at 20+.

### Precedent

This ADR retroactively describes a policy that was already applied in Phase A–E of #32 (the original TEI Model Consolidation, April 2026): `@meaningRef` → `@ana`, `@wordRef` → `@corresp`, `<seg type="pc">` → `<pc>`, `<l>` → `<lb/>` in prose, `<suppplied>` → `<supplied>` – all of these were data migrations to fit a tighter schema, not schema-relaxations to accept legacy data. ADR-013 formalizes that pattern as the project default going forward.

### Documented exception (2026-05-08, PD-001): nested `<hi>` allowed again

The original flatten migration (143 files, 36,924 instances) has not been reverted: the entire legacy stock stays flat. But since PD-001 the schema pattern `hi.content.model` permits recursive `<hi>` again, because the ARITHMETIC domain contains structures that cannot be flattened without losing meaning (struck-through fractions: `<hi rend="line-through"><hi rend="superscript">2</hi>/<hi rend="subscript">3</hi></hi>`). This compound semantics cannot be collapsed into `<hi rend="line-through superscript">`, because numerator and denominator need different rends. Performance is unremarkable (currently 2 occurrences in WIEN5206). For the schema discussion and the resolution see **PD-001** (near the top of DECISIONS.md).

The data-before-schema default stands. This exception is justified explicitly as "semantically dangerous, if one transformed the domain semantics away" (see ADR-013 §Decision: schema relaxation "only when the data migration would be disproportionately expensive or semantically dangerous").

**TEI P5 basis:** Chapters [2.2.7](https://www.tei-c.org/release/doc/tei-p5-doc/en/html/HD.html) (`<sourceDesc>`), [2.2.8](https://www.tei-c.org/release/doc/tei-p5-doc/en/html/HD.html) (electronic-to-electronic), `att.typed` (free `@type`).

## ADR-014: Verse boundaries as pre-built index fields (lineStarts / lineEnds)

**Status:** Implemented (2026-05-12, commit `ea7b0a507`)
**Context:** lemma search by verse position (#47.3, KZW request of 2026-05-11)

### Problem

Medievalist rhyme analysis needs "lemma X at the end of a verse" lookups (the old MHDBDB databases had them). Corpus index v4.0.1 had no `<l>` boundaries though, only a linear `words: ['lemma_xxx', …]` list per text. Verified via `zcat data/corpus-index.json.gz`.

Question: how do you integrate verse-start and verse-end information such that the frontend search gets an O(1) lookup per hit, without inflating the index drastically or bringing runtime XML parsing back?

### Alternatives Evaluated

**Option A: parse `<l>` at runtime from the reading view**
- Pro: no index bump
- Con: the reading view only fetches the XML file on demand; a search across 603 texts would cause 603 XML fetches
- Con: breaks the "pre-built index" architecture from ADR-001
- **Rejected:** a performance killer and an architectural break

**Option B: store `lineStarts[]` only, derive `lineEnds` from the difference**
- Pro: ~50 % less data (one array column instead of two)
- Pro: `lineEnds[i] = lineStarts[i+1] - 1` is computable
- Con: words between verses (e.g. a `<head>` or `<note>` between two `<l>`) would wrongly count as the end of the previous verse
- Con: for monotonically increasing sequences gzip compression is very effective anyway, so the size advantage disappears
- **Rejected:** semantically imprecise

**Option C: both, `lineStarts[]` and `lineEnds[]`**
- Pro: O(1) lookup for "position P is a verse start" (`P in lineStarts`) AND "position P is a verse end" (`P in lineEnds`)
- Pro: words outside `<l>` match neither start nor end (semantically correct)
- Pro: monotonically increasing int arrays gzip very efficiently (+3 MB instead of a nominal +6 MB)
- Con: index size +6 MB (34 → 40 MB gz)
- **Accepted:** semantic correctness, acceptable size, simple frontend logic

### Decision

Store both arrays per text: `lineStarts[]` and `lineEnds[]` as word indices of the `<l>` boundaries. Same length as the number of `<l>` with at least one indexed word. Empty arrays for prose texts without `<l>` (64/667 ≈ 10 %).

Schema bump to v4.1.0 (MINOR, a schema extension). Built in the build script via a single-pass `iterwalk(events=('start','end'))` with a stack, *not* via two separate `body.iter('<w>')` and `l_el.iter('<w>')` calls, because lxml element proxies can receive different `id()` values between iteration calls (bug verified during implementation: separate calls returned only the last word of each `<l>`).

### Consequences

**Positive:**
- Lemma search by verse position runs in O(L) per text (L = number of `<l>`) instead of O(W) (W = words)
- The verse-end filter is directly usable without a binary search
- 1,359,789 verse boundaries indexed across 603 verse texts
- An AGS sample verified genuine rhyme pairs (gân/begân, bant/bekant, mûzære/gewære, rote/nota, jâr/hâr)
- The data basis is open for follow-up features (#106): a rhyme dictionary per author, a rhyme-pressure metric per lemma, n-grams at the verse end, an alliteration index at the verse start, verse-length histograms

**Negative:**
- Index size +18 % (34 → 40 MB gz). With further bumps (PoS extension #27, possibly rhyme classification from #109) this quickly becomes unpleasant on slow connections; a modular index may be needed as a later strategy.
- The loader constant `INDEX_VERSION` has to be kept in sync with the build-script version, otherwise the cache invalidation logic does not fire. First forgotten on 2026-05-12 (loader at `4.0.1`, build script at `4.1.0`), repaired in `8f375bc4e`.

**Mitigations:**
- The CI workflow `index-version-check.yml` with `scripts/audit/check-index-versions.py` now enforces version consistency (commit `07c9f3244`; consolidated into `data-integrity.yml` since #125).
- The memory rule `feedback_index_version_bump.md` reminds future sessions of the three-place rule.

### Relation to ADR-001 and ADR-003

ADR-001 (pre-built indexes instead of runtime XML parsing) and ADR-003 (document-level word indexing) established the philosophy "rather be expensive in the build step than at runtime". ADR-014 continues that line for verse boundaries: extract once at index build, query as often as you like in the frontend in O(1).

## ADR-015: Authority source model (the corpus leads, ingest needs a backward sync)

**Status:** Accepted (2026-05-29, confirmed by KZW; documented in the course of #44/#115)
**Context:** the root-cause analysis of the 977 dangling cross-refs (#115) exposed a data authority model that had never been decided explicitly.

### Problem

The repository began as a one-off transformation (old MHDBDB RDF → CSV → TEI, 2025-07-22) and then became an active project with ongoing ingest (WZB, ARITHMETIC) AND ongoing manual corpus corrections. What had never been written down:

- When corpus annotation (`@lemmaRef`/`@ana`) and `lexicon.xml` diverge, which one leads?
- Who maintains the authority files (still Salzburg, or the repository)?
- How do new senses get in?

Consequence: the WZB pipeline (phase 1b, 2026-04) minted new lemma ids ≥78000 into the corpus, but no script wrote them into `lexicon.xml` (only 4 by hand, commits `8caa09627`/`649c0fe55`; many sense ids ≥78000 are structural artifacts of lemma creation). 977 refs have pointed at missing lexicon entries ever since. An earlier session wrongly read this as a "migration gap" and proposed backfilling from the archived branch, which is semantically wrong, because the repository is the master and the ids arose post-migration.

### Decision

Three binding rules, normative in [CONTRACTS.md → F. Authority Source Rules](CONTRACTS.md#f-authority-source-rules):

1. **The corpus leads, the authority follows.** If an id referenced in the corpus is missing from `lexicon.xml`/`variants.xml`, the corpus annotation is authoritative and the authority file is brought in line. Exception: an obvious typo in the corpus (an id that never existed, a single occurrence, a neighboring id existing with a fitting form) is corrected in the corpus.
2. **The repository is the sole master.** Since the migration (2025-07-22) there is no Salzburg re-export and no living external source. All 8 authority files are maintained in-repo.
3. **Ingest needs a backward sync.** Every pipeline that creates new lemma or sense ids has to write them into `lexicon.xml` atomically. Lemma stubs (form + PoS) can be generated from the corpus; the sense-to-concept assignment is **curatorial** (the team's job, not reconstructible from the corpus).

### Consequences

**Positive:**
- An unambiguous rule prevents the misreading "dangling ref = corpus error" or "backfill from the old branch".
- The cross-ref audit (`scripts/audit/check-authority-cross-refs.py --check`) is the drift detector as a CI gate (in `schema-validation.yml`; consolidated into `data-integrity.yml` since #125).
- A clear separation between what is backfillable (lemma stub) and what is curatorial (sense meaning).

**Negative:**
- Forward-only ingest pipelines (WZB) need a backfill script afterwards; until then `lexicon.xml` is exempted in the CI baseline (977 refs, G3 open in #115). *Update 2026-07-02 (#152):* the exemption is no longer blanket tolerance. The tolerated dangling ids are pinned as an id-set ratchet in `scripts/audit/lexicon-baseline.json`; every new id breaks CI (`--update-baseline` advances the ratchet after backfills).
- The sense backfill is not fully automatic (a curatorial step for KZW/Julia).

**Mitigations:**
- `scripts/audit/check-lexicon-senses.py` detects sense-less lemmata locally (regression protection since 2026-05-11).
- Future ingest pipelines (ARITHMETIC, Linda, …) have to include a `*-backfill-lexicon.py` step (follow-up requirement from #115).

### Relation to ADR-013

ADR-013 ("data before schema") and ADR-015 are complementary: ADR-013 protects existing data against schema relaxation; ADR-015 settles which data layer (the corpus) leads on authority conflicts. Both say the same thing: the data as it grew is the truth, derived artifacts follow.

### PD-001: keep or transform away the ARITHMETIC domain classification?

**Date raised:** 2026-05-07
**Date resolved:** 2026-05-08
**Status:** Resolved (middle course). The five further small ARI questions (sigle, license, author, edition, genre) are settled as well; see [`scripts/ingest/ari/README.md`](../scripts/ingest/ari/README.md).
**Issue:** [#92](https://github.com/DigitalHumanitiesCraft/mhdbdb-tei-only/issues/92)

**Complete audit finding (2026-05-08, all 6 manuscripts):** 12 element classes not contained in the current MHDBDB schema, 24 additional `<div>/@type` values, 7 additional `<hi>/@rend` tokens. All 12 elements are TEI P5 standard. RelaxNG cascade verified: stage-2 validation fails solely because of these classes.

**Decision (Katharina + Christian, Signal 2026-05-08):** the middle course. All 12 element classes, all 24 additional `<div>/@type` values and all 7 `<hi>/@rend` tokens go into the main schema `mhdbdb.rnc` as **optional elements**. In `docs/TEI-MODEL.md` they are clearly separated into "mandatory stock for every corpus" and "domain extension arithmetic (optional)".

**Rationale:**
- Admitting something to the schema means permitting it, not prescribing it. Editors of lyric poetry never have to use `<unit>`, `<rs>` and so on if they have no fractions or units of measurement.
- All 12 elements are TEI P5 standard, so no new tags are invented.
- `<unclear>` used to be present in the MHDBDB stock as an italics marker and has been lost; this admission reintroduces it.
- Standard editorial vocabulary (`<add>`, `<gap>`, `<abbr>`, `<expan>`, `<am>`, `<g>`) and onomastics (`<roleName>`, `<occupation>`, `<placeName>`) are useful across genres for future ingests.
- Domain-specific tags (`<unit>`, `<rs>`, `<figure>`, calculation-type `@type` values, fraction `@rend` values) preserve Carina's research annotation, which would otherwise be lost.
- A modular schema (a separate `mhdbdb-arithmetic.rnc`) would follow the TEI textbook more closely but is premature architecture for n=2 (WZB+ARI).

**Follow-up tasks:**
1. Schema implementation in `mhdbdb.rnc` with RNG regeneration and validation of the 667 existing files (track A, planned for the same day)
2. **Concept system connection** for `<unit>` and `<rs>`: mapping onto `concepts.xml` via `@ana`, together with Carina (after the schema admission)
3. **Reading view render policy**: keep it minimal, show only `<expan>` for abbreviations; rendering fractions, figures and calculations is a follow-up task worth funding

#### Problem

Carina's 6 Early New High German arithmetic manuscripts come with a domain classification that does not exist in the current MHDBDB schema:

- `<unit>` – units of measurement and weight as a separate inline annotation
- `<person>` – historical persons (instead of `<persName>` from TEI P5)
- `div/@type="commodity_calculation"` and `div/@type="reckoning_example"` – calculation-type classification at section level

The rest of the conversion drift (`<seg type="token">` → `<w>`, the `tei:` namespace, header completion, the xml:id scheme) can be scripted mechanically; these domain markers are the only place where semantic loss threatens.

#### Options

1. **Keep via schema extension:** allow `<unit>` and `<person>` as additional inline elements in `mhdbdb.rnc`, add the new `div/@type` values to the enum. Pro: research-relevant special annotation stays analysable. Con: the schema acquires genre-specific constructs that other texts will never use.
2. **Transform away:** `<unit>` → `<measure>` (TEI standard); `<person>` → `<persName>`; map `div/@type` onto existing values (`section`?). Pro: the schema stays clean. Con: the arithmetic-specific semantics are lost, and Carina's actual contribution becomes invisible.
3. **Hybrid:** give `<measure>`/`<persName>` a `@type` or `@ana` carrying the arithmetic classification in a TEI-conformant form. Pro: a compromise between 1 and 2. Con: requires a mapping table and documentation.

#### Who has to decide

Carina (original intention) plus Katharina (research roadmap). Until then: prepare conversion scripts for the mechanical drifts, leave the domain classification in the source files untouched.

#### Relation to ADR-013

This decision is the first to put ADR-013 ("data before schema") into practice against a genre special case: is the domain annotation existing data that the schema has to accept, or data that gets migrated to our schema? A decision sets a precedent for future special corpora (Linda, Minnereden, CoReMA).

## ADR-016: stage 3 of lemma resolution matches prefixes, not substrings

**Status:** Accepted (2026-07-28, in the course of #224; also resolves item #45 from #169)
**Context:** external bug report by Klaus Schmidt, verified against the deployed authority index.

### Problem

Stage 3 of the three-stage resolution (CONTRACTS.md §C) was a bidirectional substring test:

```js
lemma.normalized.includes(query) || query.includes(lemma.normalized)
```

The second direction hits every short lemma that sits anywhere inside the input. The lexicon holds 5 one-letter, 98 two-letter and 598 three-letter normalized forms; they matched practically every input that reached stage 3 at all. `minnecl` returned 16 hits (led by `i`, `unminneclîche`, `nec`), `schwertkampf` 14 (`a`, `êr`, `wert`, `kamp`).

**The bug report had two causes, and the first was nearly overlooked.** The search for „böses" shown there did not carry an ordinary ö: Klaus Schmidt had copied from the WZB reading view, and the Wenzelsbibel writes umlauts with a **breve** (`o` + U+0306). The normalizer knew neither the decomposed form nor the breve; the input therefore missed stages 1 and 2 (the variants map holds the key `boeses`) and only then landed in stage 3. There the substring test turned the failure into three false hits. That also explains why `bœse` is missing from the screenshot although it is the right answer.

To Klaus Schmidt this looked like a problem with the new WZB vocabulary. It half was: the Wenzelsbibel contributed 830 breve tokens, and no other of the 667 texts has a single one. The fix therefore consists of two parts that only work together: NFC composition pulls `o` + U+0306 together into `ŏ`, and the new breve rule turns that into `oe`. Remove either place and the reported case breaks again. Independently of that, the stage-3 rule applies to every input that ends up there.

Second finding: the rule existed twice and had drifted. The main site tested bidirectionally, the playground in one direction only (lemma contains input). The same input returned different sets depending on the interface, documented as #169 item #45.

### Options

1. **Put a minimum length on the substring test.** Minimally invasive, but keeps the infix hits: „minnen" would still find `innen` and `i`.
2. **Prefix matching in both directions**, with the minimum length only on the suffix side. Exploits the fact that Middle High German inflection is suffixal.
3. **Drop stage 3 entirely.** Cleanest for precision, but removes the truncation search („minn" finds „minne") that users expect.

Chosen: **option 2**, together with NFC composition in the normalizer against cause 1 (contract A, step 0).

### Decision

Stage 3 accepts a candidate if `lemma.normalized` begins with the input (stem input) or the input begins with `lemma.normalized` (inflected input) and the lemma has at least 3 normalized characters. Results are sorted by length difference to the input; the playground breaks ties by corpus frequency (ADR context #163/#164).

The predicate and the ranking distance live as pure functions in `assets/js/lib/lemma-resolve.js` and are imported by both interfaces. Deliberately shared is **only stage 3**, not the whole orchestration: the main site reads a precomputed `lemma.normalized`, the playground normalizes at runtime and additionally ranks homographs by frequency. The pattern follows `lemma-match.js` (ADR context #126/#130).

### Consequences

Measured over 300 variant forms with a known target lemma, drawn with a fixed seed, stages 1 and 2 bypassed (`scripts/audit/measure-stage3-resolution.py`):

| Metric | old | old + new ranking | new |
|--------|----:|--------------------:|----:|
| Recall (target anywhere in the list) | 11.3 % | 11.3 % | 10.7 % |
| Top-1 after ranking | 0.3 % | 9.3 % | 10.0 % |
| Median list size | 8 | 8 | 0 |
| Largest list | 108 | 108 | 8 |

The middle column belongs there, otherwise the top-1 jump reads as a thirtyfold effect of the rule. It comes almost entirely from the new sort by length difference; the rule itself contributes 9.3 % → 10.0 %. Its actual gain is in the bottom two rows.

- **The median of 0 is intended.** For an unknown form stage 3 now usually returns nothing instead of eight false hits; the interface then shows its no-hit state. An honest "not found" is worth more to a philological tool than a plausible-looking misdirection.
- **Recall loss of 2 out of 300**, both prefix breakers: `gewieren` → `wieren` (prefix `ge-`) and the Roman numeral `ccccxli`. Both are attested variants and are already resolved by stage 2 in real use.
- **The playground's infix discovery is gone.** An input that reaches stage 3 at all no longer hits lemmata that carry it only word-internally (old rule: „lantwin" contains „win", new rule: no hit). The caveat matters: `wîn` is itself a lemma and `wein` an attested variant, so both inputs are caught by stage 1 or 2 and never see the fallback. Compounds are reached through the word-component search in the lemmata explorer (#239). This is a separate source of noise, not the one from #224: the noise there (`ês`, `ô`, `sê`) came from the direction "input contains lemma", which only the corpus search had. Anyone looking for compounds has the lemmata explorer.
- **Ablaut and umlaut stay unsolved** (`slüege` → `slahen`). The old test did not find those either, it merely returned random junk. A real solution would be stemming or an inflection table and belongs to #109.
- **Measurement bias:** real stage-3 inputs are more often New High German words and typos than Middle High German inflected forms. The sample shows whether the fix costs recall, not how often stage 3 finds the right thing in everyday use.
- **The authority index changes** (v1.6.1 → v1.6.2). Not because of the stage-3 rule, which is pure frontend, but because of step 0. Three records with a decomposed ü were unfindable through normalized search: `person_1052` (Hugo von Mühldorf), `person_1332` (Wachsmut von Mühlhausen) and `work_435`. Lemmata and variants are unchanged.
- **The WZB ingest track gains as well, but has not been followed up yet.** `wzb-auto-match.py`, `wzb-sense-assign.py` and `wzb-sense-apply.py` normalize through the same function. **289 WZB `<w>` with an o/u breve still carry no `@lemmaRef`**, because the breve stopped the matcher. A re-run of the matcher under this rule will resolve some of them; that is backfill work on the data side and belongs in its own run, not in this frontend PR.
- **The breve stays unsolved on 136 WZB tokens, 64 of them lemmatized.** The rule covers `ŏ` and `ŭ`, so 405 of the 469 lemmatized breve tokens. The rest sit on `w` (91 tokens, 48 lemmatized) and `n` (22, of those 16), plus single cases on y/a/v/r/m/i/e/z. There the breve is not an umlaut sign but a Bohemian writing convention: `few̆er` stands for `viur`, `ew̆er` for `ir`, `wenn̆` for `wan`. Anyone copying these forms out of the reading view still lands in the fallback. A rule for them would be an editorial decision about the WZB transcription, not a technical one, and therefore belongs to KZW, not in this ADR. (Decided on 2026-08-06 for the 113 tokens on `w` and `n`: the breve is stripped, see ADR-017. The 23 remaining tokens stay untouched.)
- **The keyness column of the table view** (#114) uses the same `resolveLemmaIds` reference set. For stage-3 search terms the log-likelihood values therefore change, because the reference sum runs over fewer lemmata.
- **The minimum length of 3 lets fragments through.** „heldentum" finds `hel` as its only hit, „treueschwur" finds `tre`. Consumers of `matches[0]` in the playground take that silently. It is better than the previous 14 random hits, but not a good result; raising the threshold would be the next adjustment if users complain.

## ADR-017: the breve over `w` and `n` is stripped, not expanded

**Status:** Accepted (2026-08-06, in the course of #235 point 3; answers the question ADR-016 deferred)
**Context:** editorial decision by Julia Hintersteiner as the WZB editor, measured against the built authority index.

### Problem

ADR-016 made the breve an umlaut sign for `ŏ` and `ŭ`, and explicitly left the remaining base characters open: „a rule for them would be an editorial decision about the WZB transcription, not a technical one, and therefore belongs to KZW, not in this ADR."

The open remainder is not evenly spread. Of the 830 breve tokens in the Wenzelsbibel, 694 sit on o/u and are covered by ADR-016. Of the remaining 136, **113 sit on `w` (91) and `n` (22)**, and 64 of those carry a `@lemmaRef`. The other 23 are single cases across y/a/v/r/m/i/e/z, none of them lemmatized.

On `w` and `n` the breve is not an umlaut sign. It is a Bohemian writing convention, and the annotation of the corpus says so itself: `few̆er` carries a `@lemmaRef` to `lemma_7108` (`viur`, fire), `ew̆er` to `lemma_56117` (`ir`), `wenn̆` to `lemma_7385` (`wan`). The base letter is what the word is built from; the breve says nothing about the vowel.

Consequence before this decision: `w` + U+0306 and `n` + U+0306 have **no precomposed form**, so step 0 (NFC) leaves them standing and every later rule misses them. Measured against the built index with the three resolution stages of CONTRACTS §C, **11 of the 113 tokens were findable** by typing the form, all eleven only through the stage-3 fallback, and **not one of the 64 lemmatized ones**. Anyone copying such a form out of the reading view got the no-hit state for a word the corpus has annotated.

### Options

1. **Expand to a digraph, as with `ŏ`/`ŭ`.** Parallel to the existing rule, but wrong on the facts: there is no umlaut to resolve, and `weer`/`neer` matches nothing.
2. **Strip the breve, keep the base letter.** Follows what the corpus annotation already assumes.
3. **Leave the normalizer alone and fix it in the data:** write the breve forms into `variants.xml` as attested forms. Keeps the normalizer minimal.
4. **Leave it open, and backfill `@lemmaRef` on the 49 unlemmatized tokens instead.** Helps the corpus, not the person typing the form.

Chosen: **option 2.**

Option 3 fails on the data: not one of the 113 tokens carries a `@corresp`, so none of them ever entered `variants.xml` (0 keys with a breve in the built map). Taking that path would mean inventing variant entries rather than deriving them from the corpus, against the rule that `variants.xml` is corpus-derived (CONTRACTS §F). Option 4 is orthogonal and stays open as backfill work in #235 point 3: it makes tokens findable **through** a lemma, this decision makes the typed form itself resolve, and 49 of the 113 tokens have no lemma to be found through.

### Decision

After the `ŏ`/`ŭ` rules, and after lowercasing, the normalizer removes the combining breve on `w` and `n` and keeps the base letter:

```text
w + U+0306 → w        n + U+0306 → n
```

Both places implement it with escapes rather than literals (`'w̆'`), because a combining mark in source code is invisible and an editor with automatic normalization could change it silently. The two rules stand in `assets/js/lib/text-normalizer.js` and `scripts/mhg_normalizer.py`, are contract A in CONTRACTS.md and are covered by three parity test cases (`few̆er`, `wenn̆`, and `Ew̆er` for the uppercase path).

The breve on the remaining 23 tokens stays untouched. The reason is not a missing precomposed form (for a/e/i one exists and step 0 produces it), but that there are too few attestations and not one of them is lemmatized: `hălses`, `nămen`, `geslăgen`, `schĕpfen`, `erschĭnen`.

### Consequences

Measured with `scripts/mhg_normalizer.py` against `data/authority-index.json.gz`, over all 113 tokens, resolution through stages 1 to 3 as in CONTRACTS §C:

| | findable | stage 1 | stage 2 | stage 3 | no hit |
|---|---:|---:|---:|---:|---:|
| before | 11 | 0 | 0 | 11 | 102 |
| after | 100 | 0 | 93 | 7 | 13 |

- **For all 64 lemmatized tokens the first hit is exactly the lemma the token itself carries.** No lemmatized token resolves to a different lemma, and none needs the ranking to get there.
- **The resolution runs through stage 2, not stage 3**, because the same words are spelled without a breve elsewhere in the corpus and are in the variants map as `fewer`, `ewer`, `wenn`. The rule does not create a new match; it lets the WZB spelling reach one that already existed.
- **Both indexes and the API stay byte-identical.** The rule changes the normalization of user input, and no authority record carries a breve on `w` or `n` (0 of 234,243 variant keys). Verified by a full rebuild on 2026-08-06: `build-corpus-index.py`, `build-authority-index.py`, `build-api.py`, no diff, hence no version bump (per the rule „do not set a bump without a change of content", DATA-MODEL.md).
- **13 tokens in 10 forms still find nothing**, all of them unlemmatized and most of them compounds: `new̆komen` (4), plus `strew̆te`, `hew̆es`, `bow̆te`, `strew̆ende`, `vrew̆te`, `bow̆o`, `vngesow̆erteigtes`, `mow̆ern`, `gemaw̆erte`. They fail on the compound, not on the breve, and the word-component search (#239) is the path for them.
- **The measuring rule matters more than the number.** „113 tokens" counts `<w>` elements whose NFD text contains `w` or `n` plus U+0306, in `tei/WZB.tei.xml`, `@lemmaRef` irrelevant. Counted after NFC, or per distinct form (40), or only for lemmatized tokens (64), the same fact yields a different number. This is the lesson of 2026-07-31: a number without its measuring rule gets falsified when someone „corrects" it.
- **The reverse direction is not covered.** Typing `fewer` finds the lemma, and through the lemma the annotated tokens. It does not highlight the 49 unlemmatized breve tokens in the reading view; only a `@lemmaRef` does that. That is #235 point 3.

## ADR-018: attribution of curated lemma statements stops at the data layer, for now

**Status:** Accepted (2026-08-07, resolves #270 from the review of PR #268)
**Context:** the curated productions in `lexicon.xml` carry a mandatory `@resp`, and no interface shows it.

### Problem

Since 2026-07-30 three optional productions in `lexicon.xml` hold curated prose: `<etym type="borrowing">`, `<def>` and `<note type="comment">` (TEI-MODEL-AUTH-FILES §3.1). All three carry `@resp` pointing at `contributors.xml#contrib_N`, required on both `<note>` types, with the stated reason that a comment without an author is not citable.

The authority index transports the values (`origin.resp`, `senses[].definitionResp`, `senses[].commentResp`) and the API passes them on. Neither the lemma page nor the playground displays anything: `contributors.xml` is deliberately not part of the authority index, so the frontend cannot turn `contrib_003` into a name. The mandate therefore buys nothing a reader can see, which is the opposite of what it was written for.

Measured against the built index (Authority Index v1.8.0, 2026-08-07): 43,879 lemmata, of which **1 carries `origin.resp`, 1 a `definitionResp` and 1 a `commentResp`**, all three on `lemma_37818` (`Abba`) and all three pointing at `contrib_003`. `contributors.xml` holds 52 persons and 2 organisations.

### Options

1. **A lean contributor map in the authority index.** ID plus display name for all 54 records. Measured: 1,719 bytes raw, **764 bytes gzipped**, against an index of 3.1 MB, so 0.02 percent. The interface can then draw the name. Costs an index bump across the five gated places, a new top-level key that becomes a promise to API consumers (CONTRACTS §G), and a renarration of the "seven of eight files are indexed" statement wherever it stands: INDEX.md, DATA-MODEL.md, CONTRACTS.md, RESEARCH.md, TEI-MODEL-AUTH-FILES.md, ADR-001 in this file, `README.md` (twice, and the table row on the index contents would become plain wrong), and `totalAuthorityFiles = 7` in `playground/js/ui/core/ui-helpers.js:516`, the counter KZW queried once in #105.
2. **Resolve at build time and denormalize.** The build reads `contributors.xml` and writes the resolved display name next to each `*Resp`. No new collection, no scope change, no 7-against-8 renarration; the index keeps its shape and gains three optional strings, following the `altNames[]`/`altNormalized[]` pattern of index-parallel fields. Cost at scale is not measured, because the scale is set by #28 layer B and is not yet known.
3. **Leave it on the data layer.** The status quo, documented in TEI-MODEL-AUTH-FILES §3.1 and CONTRACTS §G.3, but until now not justified there.

Chosen: **option 3, for now**, with a named trigger. The choice between 1 and 2 is deliberately left open and belongs to whoever implements the trigger.

### Decision

The authority index stays at seven content-bearing files. Curated prose is displayed without an attribution until one of these two things happens:

- **more than 25 lemmata carry a curated statement**, or
- **#28 layer B writes origin data in bulk**, whichever comes first.

**Cost is not the reason for waiting.** 764 bytes settle that, and the number stands here so nobody re-litigates it. Two other things are:

- **At n=1 the display question cannot be answered honestly.** Where an attribution belongs on a scholarly lemma page, how it reads next to a source citation, and whether it appears in the playground at all, is a decision for KZW about a user-visible page, not one to derive from a single example.
- **#28 layer B will not deliver what this issue assumes.** The phase plan (`docs/features/FREMDSPRACHEN-PHASENPLAN-28.md`, in the revision of 2026-07-29 that carries the layer A/B split) gives layer B "source language plus source of the attribution (Lexer/MWB/Kluge/LLM with a confidence value)". That source is bibliographic, not a person, and `contributors.xml` models neither dictionaries nor pipelines. So bulk origin data raises a second question, "who or what vouches for this", which `@resp` in its present form does not answer. Deciding the contributor map before that question would build the wrong resolution mechanism, and thousands of lemma pages reading "nach Katharina Zeppezauer-Wachauer" would be noise where "Lexer, accepted by the pipeline" is information.

### Consequences

- **The mandate on `@resp` stays, and stays without visible effect.** Accepted deliberately: the value is in the data and in the API, it is citable from there, and a required attribute is far cheaper to keep than to reintroduce later against existing entries. What is not acceptable is leaving it undated, hence the trigger.
- **The 25-lemma threshold is a stop sign, not a target.** It is set low on purpose. Anyone who curates the 26th lemma without having settled the display question has taken the decision by omission.
- **API consumers are unaffected.** No field is removed or changed. `*Resp` keeps carrying `contributors.xml#contrib_N` verbatim, and resolving it keeps needing the XML file. Both options 1 and 2 would be purely additive later.
- **The audit gap stays open too.** That a `contrib_N` exists at all is checked only by `scripts/audit/audit-authority-files.py`, which does not run in CI, so a well-formed but unbacked ID validates green (TEI-MODEL-AUTH-FILES §3.1). At n=1 that is tolerable. It becomes a real gap at the same moment the trigger fires, and belongs to the same work package.
- **The counting rule for the trigger:** entries in `lexicon.xml` carrying at least one `@resp` on `<etym type="borrowing">/<note>`, `<def>` or `<note type="comment">`. Measured on the built authority index as the number of lemma records with a non-empty `origin.resp`, `senses[].definitionResp` or `senses[].commentResp`. Today that is 1.

## ADR-019: the index budget warns instead of failing, and its two thresholds pull a split in opposite directions

**Status:** Accepted (2026-08-08, answers the "write an ADR" half of #111. **No migration is triggered**: the corpus index sits at 84 percent of its budget.)
**Context:** #111 has been an open trigger reminder since 2026-05-12, asking for a soft cap on index size and a splitting strategy to have ready when it fires.

### Problem

The pre-built indexes are the price of ADR-001 (no runtime XML parsing). They grow with every annotation pass and with every new per-word field, and nothing measured that growth: the threshold in #111 lived in the issue body, so it could only fire if a human happened to re-measure. Twice someone did (2026-08-05, 2026-08-07), which is precisely the manual labour a gate should absorb.

Two things had to be settled before any splitting option could be judged: what the budget actually is, and which field spends it.

### What was measured

All figures are decimal MB (1 MB = 1,000,000 bytes), measured 2026-08-08 against the shipped files (Corpus Index v4.2.1, Authority Index v1.8.0).

**The unit was itself the first finding.** #111 records 42 MB for `data/corpus-index.json.gz` (2026-05-12) and the comment of 2026-08-07 records 40.2 MB. Both are correct, and the gap between them is a unit, not a shrinkage. The May file (`ea7b0a507`) held 42,183,990 bytes, which is 42.18 decimal MB and 40.23 MiB; today's file holds 42,165,752 bytes, and the 40.2 of 2026-08-07 is exactly its MiB value (that comment's own measuring rule divides by 1048576 and calls the result MB). So the corpus index has been **flat since that May measurement**: 12 commits have touched the file since, never more than 19 kB apart, endpoints 18 kB, and it has been byte-identical since 2026-07-31. It did not fall by 4 percent. (Reaching one commit further back does change the picture: on 2026-05-08 the file still held 35.8 MB. The flat stretch starts at the measurement, not at the start of the month.) Since the thresholds of 50 and 200 were set in the decimal measurement, decimal MB is the unit this budget is denominated in. `check-file-sizes.py` (#350) keeps counting in MiB because GitHub's wall is stated in MiB; the two scripts therefore differ by 4.9 percent on the same file, deliberately.

**Corpus index, 42.17 MB gz / 168.34 MB raw.** Per field, where the gz column is the compressed size of that field concatenated across all 667 texts (so the column is indicative and not exactly additive; it sums to 98 percent of the file):

Measuring rule for the raw column: the value of that field serialised per text with `json.dumps(v, ensure_ascii=False, separators=(',',':'))` and summed over all 667 texts, so it excludes the key name, the colon and the array punctuation around it. Serialising the eight metadata fields as one array each instead adds 5,344 bytes of brackets and commas and yields 0.070 MB; that is the same data under a different rule, not a correction.

| field | raw MB | gz MB | ratio | share of the wire |
|---|---|---|---|---|
| `texts[].lemmata` | 51.2 | 21.5 | 2.38x | **51.1 %** |
| `texts[].words` | 97.7 | 13.0 | 7.52x | 30.8 % |
| `texts[].lineStarts` | 7.8 | 3.1 | 2.54x | 7.3 % |
| `texts[].lineEnds` | 7.8 | 3.1 | 2.54x | 7.3 % |
| `lemmaIndex` | 3.7 | 0.6 | 5.92x | 1.5 % |
| the 8 metadata fields | 0.064 | | | 0.04 % |

**Authority index, 3.29 MB gz / 23.57 MB raw:** `lemmata` 52.9 percent of the wire, `variants` 27.8, `maps` 14.5, `works` 3.0, everything else together 1.8.

### The finding that redirects the strategy

Option A of #111 proposes to split `words` out and keep a core of "10 to 15 MB gz". Measured, that does not hold, because **compression is wildly uneven across the fields**. `words` is 58 percent of the index in memory but only 31 percent on the wire: 7.5 million tokens drawn from 42,630 distinct values compress 7.5-fold. The integer position arrays in `lemmata` compress only 2.4-fold, so they are 30 percent of the raw index and **51 percent of the download**. Moving `words` out therefore leaves a core around 29 MB gz, not 10 to 15.

The consequence is that the two thresholds of this budget are not two views of one problem, they are two problems:

- **The gz threshold is about the wire and the cache.** To move it, `texts[].lemmata` has to go.
- **The raw threshold is about RAM after `JSON.parse`.** To move it, `texts[].words` has to go.

Whichever is breached first decides which field moves. Deciding that in advance, as #111 attempted, would have picked the wrong field for the gz case.

A second measured redundancy is worth recording for whoever implements a split: the same 7,533,010 lemma occurrences are encoded three times over, as `texts[].words`, as `texts[].lemmata` (inverted, with positions) and as `lemmaIndex` (the 513,206 text-lemma pairs, derivable from `texts[].lemmata` alone). Roughly 90 percent of the raw index is one dataset in three representations. That is a compression opportunity no splitting scheme addresses, and it may well be cheaper than splitting.

### Decision

1. **The budget is gated, and the gate warns.** `scripts/audit/check-index-budget.py` measures every `data/*.json.gz` on both axes and runs in `data-integrity.yml`. It exits 0 even when a budget is breached; it turns red only when the measurement itself fails. Reason: an overrun is not a defect in the commit that triggers it. The index grows through legitimate annotation work, and a red gate would block the next backfill until somebody had built a splitting scheme. What the gate owes us is that the moment is not missed, not that it is prevented.
2. **Thresholds:** corpus index 50 MB gz / 200 MB raw, taken unchanged from #111. Authority index 8 MB gz / 60 MB raw, newly set here, from its own level with room for the #115 backfill. Curated add-on indexes of the #194 category default to 5 MB gz / 40 MB raw.
3. **No splitting today, and no option pre-selected.** At 84 percent utilisation the cost of choosing early is real and the benefit is zero. What is fixed here is the rule for choosing: **the breached axis names the field**, per the table above.

### Consequences

- **`maps` is the one free win, and it is in the other index.** It is 14.5 percent of the authority download and is read by exactly one file, `playground/js/playground-main.js:147-157`, feeding two drill-downs. `korpus.html`, `woerterbuch.html` and every lemma page fetch and parse 2.5 MB of raw data they never touch. This needs no ADR and no splitting scheme, and it is not done here because it is a frontend change with its own tests, not a measurement.
- **Utilisation is the number to watch, not headroom in MB.** The authority index has less absolute room to its threshold (4.7 MB) than the corpus index (7.8 MB), yet it sits at 41 percent against 84. The gate sorts and reports by utilisation for that reason.
- **The next trigger is a feature, not a date.** #27 (per-word POS) is estimated at 3 to 5 MB gz and #109 (NER) at 5 to 10. POS stays inside the budget even at the top of its range (47.2 MB); NER breaches it alone at the top of its range (52.2 MB); together they breach it in **every** combination, including both estimates at their lower bound: 3 plus 5 is 8 MB against 7.83 MB of headroom. The gate will say so on the first index build that carries them.
- **A split would blind this gate.** It measures per file against a per-file threshold, so after a split every part would sit below its threshold while the total load was unchanged. Whoever implements a split converts the gate to summing over the parts in the same work package. This is the one hard dependency the gate has on this ADR.
- **`totalLemmata` already exists and is unused.** `playground/js/playground-main.js:319-324` walks `Object.keys(text.lemmata)` across all 667 texts at first paint purely to render a count, holding 51.2 MB in the critical path for a display number, while the index already carries a top-level `totalLemmata` that nothing reads. Any lazy-loading scheme has to defeat this line first, so it is worth fixing before, and independently of, any split.
- **#111 asked for ADR-015.** That number went to the authority source model in 05/2026, as the comment of 2026-08-05 already warned. This is ADR-019.
